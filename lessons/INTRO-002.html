Why React?

1 · Visual Introduction

Picture a shop window display. When stock changes, a good shop has one rule: "the display always matches the stockroom". React gives your page that rule: UI = function(data) (UI is computed from state).

   DATA (state)                         SCREEN (UI)
 +------------------+     React      +--------------------------+
 | cart = [         |  ==========>   | Cart (2)                 |
 |   'Pizza',       |   re-renders   |  - Pizza                 |
 |   'Coke'         |   for you      |  - Coke                  |
 | ]                |                |  Total items: 2          |
 +------------------+                +--------------------------+
        |  add 'Fries'                         ^
        v                                      |
 cart = ['Pizza','Coke','Fries']  ---- React ---+  badge, list, total all update

Three problems React solves:

  1. Sync — the screen always matches the data.
  2. Reuse — build a piece once, use it everywhere.
  3. Scale — big apps stay organised as a tree of small parts.

2 · Why Do We Need It?

Wrong
// Vanilla: 3 places show the cart; update each by hand
let cart = ['Pizza', 'Coke'];
function addItem(item) {
  cart.push(item);
  document.getElementById('badge').textContent = cart.length;
  document.getElementById('list').innerHTML +=
    '<li>' + item + '</li>';
  // Forgot the total line? It is now wrong.
}
Fixed
// React: change data once, every view follows
const [cart, setCart] = useState(['Pizza', 'Coke']);
function addItem(item) {
  setCart([...cart, item]);
}
// badge, list and total all read from cart
<Badge count={cart.length} />
<CartList items={cart} />
<Total count={cart.length} />

3 · Core Concept

  • Single source of truth (state) — data lives in one place; the UI reads from it.
  • Automatic re-render — calling a state setter tells React to run the component again.
  • Reconciliation (diffing) — React compares the new output with the old and changes only what differs in the real DOM.
  • Reusable components — one ProductCard, many products.
  • Composition (building big from small) — components nest inside components.
  • One-way data flow — data goes down via props, events go up via callback functions. Easier to trace bugs.
  • Huge ecosystem — routing (React Router), frameworks (Next.js), mobile (React Native).

4 · Syntax

import { useState } from 'react';

// state: [currentValue, setterFunction]
const [items, setItems] = useState([]);

// update by giving a NEW value (do not mutate)
setItems([...items, 'Fries']);

// pass data down as props
<CartList items={items} />

// pass a callback down so the child can ask for changes
<AddButton onAdd={() => setItems([...items, 'Fries'])} />

5 · Practical Example

A food cart where the badge, list and total stay in sync automatically. Vite app, src/App.jsx (main.jsx is the default Vite one using createRoot):

import { useState } from 'react';

const menu = ['Pizza', 'Burger', 'Fries', 'Coke'];

function Badge({ count }) {
  return <span>Cart ({count})</span>;
}

function CartList({ items }) {
  if (items.length === 0) return <p>Your cart is empty</p>;
  return (
    <ul>
      {items.map((item, i) => (
        <li key={i}>{item}</li>
      ))}
    </ul>
  );
}

function MenuButton({ item, onAdd }) {
  return <button onClick={() => onAdd(item)}>Add {item}</button>;
}

export default function App() {
  const [cart, setCart] = useState([]);

  function handleAdd(item) {
    setCart([...cart, item]);
  }

  return (
    <main>
      <header>
        <h1>QuickBite</h1>
        <Badge count={cart.length} />
      </header>
      <div>
        {menu.map((m) => (
          <MenuButton key={m} item={m} onAdd={handleAdd} />
        ))}
      </div>
      <CartList items={cart} />
      <p>Total items: {cart.length}</p>
    </main>
  );
}

After clicking "Add Pizza" then "Add Coke":

QuickBiteCart (2)

  • Pizza
  • Coke

Total items: 2

7 · Execution Flow

 User clicks "Add Pizza"
        |
 onClick -> onAdd('Pizza') -> handleAdd('Pizza')
        |
 setCart([...cart, 'Pizza'])     (schedules an update)
        |
 React re-runs App() with cart = ['Pizza']
        |
 New output: Badge count=1, CartList items=['Pizza'], Total 1
        |
 React diffs old vs new output
        |
 Only changed DOM bits update: "Cart (1)", new <li>, "Total items: 1"

8 · Real-World Application

  • Food delivery — cart badge, checkout page and order summary all read the same cart state.
  • Chat — unread count in the tab, sidebar and title stay equal.
  • Weather app — switch °C/°F once; every temperature on screen updates.
  • Large teams — each team owns components (search, player, profile) without stepping on each other.

9 · Common Mistakes

Mistake 1: mutating state directly

Wrong
function handleAdd(item) {
  cart.push(item);   // same array object
  setCart(cart);     // React sees no change, may skip render
}
Fixed
function handleAdd(item) {
  setCart([...cart, item]); // new array
}

Mistake 2: storing a copy of data that can be calculated

Wrong
const [cart, setCart] = useState([]);
const [total, setTotal] = useState(0);
// must remember to update both -> drift
Fixed
const [cart, setCart] = useState([]);
const total = cart.length; // derived, always correct

Mistake 3: calling the handler instead of passing it

Wrong
<button onClick={handleAdd('Pizza')}>Add</button>
// runs during render -> infinite re-render error
Fixed
<button onClick={() => handleAdd('Pizza')}>Add</button>

Challenge

Todo app: add todos from an input; show list and "N left" count, both derived from one array.

Solution
import { useState } from 'react';

export default function App() {
  const [todos, setTodos] = useState([]);
  const [text, setText] = useState('');

  function add() {
    if (!text.trim()) return;
    setTodos([...todos, { id: Date.now(), text }]);
    setText('');
  }

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <button onClick={add}>Add</button>
      <ul>{todos.map((t) => <li key={t.id}>{t.text}</li>)}</ul>
      <p>{todos.length} left</p>
    </div>
  );
}

11 · Quick Revision

  • React keeps UI in sync with data: UI = f(state).
  • Change state with the setter; never mutate.
  • React re-renders and updates only changed DOM parts.
  • Components give reuse; composition gives scale.
  • Derive values (totals, counts) instead of storing duplicates.
  • Data down via props, events up via callbacks.

12 · Interview Corner

What main problem does React solve?

Keeping the UI consistent with changing data, without writing manual DOM update code for every change.

What is reconciliation?

React's process of comparing the new render output with the previous one and applying the minimal set of DOM changes.

Why is one-way data flow helpful?

Data has one owner and moves in one direction, so you can trace where a value came from and who changed it.

Does React always make apps faster?

Not automatically. It makes UI updates predictable and usually efficient, but poor patterns (huge re-renders, heavy work in render) can still be slow.

A · Concept in 30 Seconds

React solves three problems: keeping the screen in sync with data (state drives UI), reusing UI pieces (components), and scaling big apps (a tree of small, owned parts with one-way data flow).

B · Important Syntax

const [value, setValue] = useState(initial);
setValue(newValue);                 // triggers re-render
setList([...list, item]);           // new array, no mutation
<Child data={value} onChange={setValue} />

C · Must-Know Points

  • UI = function(state).
  • State setters schedule a re-render; they don't change the variable immediately.
  • React compares outputs and patches only differences in the DOM.
  • Never mutate state; create new arrays/objects.
  • Derived data should be calculated, not stored.
  • Props are read-only for the child.
  • Components can be reused with different props.

D · Interview Questions

Basic

Name three benefits of React.

Automatic UI sync with state, reusable components, and a large ecosystem/community.

Intermediate

Why must state updates be immutable?

React compares old and new values with Object.is. Mutating keeps the same reference, so React may think nothing changed.

Advanced

How does React decide which DOM nodes to update?

It diffs element trees by type and position (and key for lists). Same type: update attributes; different type: replace the subtree.

Tricky

Is "virtual DOM" the reason React exists?

No. The main idea is declarative UI from state. Diffing an in-memory tree is an implementation detail that makes that practical.

E · Output-Based Questions

const [n, setN] = useState(0);
function click() {
  setN(n + 1);
  setN(n + 1);
}
// one click, what is n after re-render?
Answer
1

Both calls use the same n (0) from this render. Use setN(prev => prev + 1) twice to get 2.

F · Debugging Questions

function add(item) {
  cart.push(item);
  setCart(cart);
}
// list does not update. Why?
Answer

Same array reference, so React bails out. Fix: setCart([...cart, item]).

G · Scenario-Based Questions

Your weather app shows °C on the card but °F in the header after toggling. What design fixes it?

Keep one unit state at the common parent, pass it down to both components, and format temperatures from it.

H · Coding Challenges

A movie list with a "Watched" button per movie and a header "Watched: N".

Solution
import { useState } from 'react';
const movies = ['Up', 'Coco', 'Dangal'];

export default function App() {
  const [watched, setWatched] = useState([]);
  return (
    <div>
      <h2>Watched: {watched.length}</h2>
      {movies.map((m) => (
        <p key={m}>
          {m}{' '}
          <button
            disabled={watched.includes(m)}
            onClick={() => setWatched([...watched, m])}
          >Watched</button>
        </p>
      ))}
    </div>
  );
}
