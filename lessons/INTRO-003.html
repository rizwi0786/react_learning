Problems with traditional DOM manipulation

1 · Visual Introduction

Imagine a restaurant with a kitchen order book (data) and a wall board (screen). With manual DOM updates, a waiter must rewrite the board by hand after every order. Miss one rewrite and the board lies.

  DATA (JS variables)            SCREEN (DOM)
 todos = 3 items       ---X---   "2 items left"   <-- forgot to update
 done  = 1             ---ok--   strike-through on item 1
 filter = "active"     ---X---   still shows completed items

 Every arrow is code YOU must write and remember.
 Miss one  ==>  UI drifts out of sync with data (stale UI)

2 · Why Do We Need It?

Wrong
// Imperative (step-by-step) updates in many places
function addTodo(text) {
  todos.push(text);
  const li = document.createElement('li');
  li.textContent = text;
  list.appendChild(li);
  // counter not updated -> shows old number
}
function deleteTodo(i) {
  todos.splice(i, 1);
  list.children[i].remove();
  counter.textContent = todos.length + ' left';
}
Fixed
// Declarative: describe the screen from data
function TodoApp() {
  const [todos, setTodos] = useState([]);
  return (
    <>
      <ul>{todos.map(t => <li key={t.id}>{t.text}</li>)}</ul>
      <p>{todos.length} left</p>
    </>
  );
}
// add/delete only change todos; screen follows

3 · Core Concept

  • Imperative code (giving step-by-step instructions) — you tell the browser each change: create, append, remove, set text.
  • State drift (UI out of sync) — data and DOM are two copies; any missed update leaves them different.
  • Update paths explode — N actions x M places on screen = N x M bits of update code.
  • innerHTML rebuild problems — wipes input text, focus and listeners; unsafe with user text (XSS, script injection).
  • Event listener leaks — re-adding listeners on every render causes double clicks firing twice.
  • DOM as storage — reading values back from the DOM (li.textContent) mixes data and display.
  • React fixes these by making the DOM an output of state, not a second copy you maintain.

// Typical vanilla DOM API calls (imperative)

5 · Practical Example

Vanilla version with a hidden drift bug (index.html)

<!doctype html>
<html>
  <body>
    <input id="text" placeholder="New todo" />
    <button id="add">Add</button>
    <ul id="list"></ul>
    <p id="count">0 left</p>
    <script>
      const todos = [];
      const list = document.getElementById('list');
      const count = document.getElementById('count');
      const input = document.getElementById('text');

      document.getElementById('add').addEventListener('click', () => {
        const text = input.value.trim();
        if (!text) return;
        todos.push({ text, done: false });

        const li = document.createElement('li');
        li.textContent = text;
        li.addEventListener('click', () => {
          const t = todos.find((x) => x.text === text);
          t.done = !t.done;
          li.style.textDecoration = t.done ? 'line-through' : 'none';
          // BUG: forgot to update count here
        });
        list.appendChild(li);
        count.textContent = todos.filter((t) => !t.done).length + ' left';
        input.value = '';
      });
    </script>
  </body>
</html>

React version — src/App.jsx (Vite)

import { useState } from 'react';

export default function App() {
  const [todos, setTodos] = useState([]);
  const [text, setText] = useState('');

  function add() {
    if (!text.trim()) return;
    setTodos([...todos, { id: crypto.randomUUID(), text, done: false }]);
    setText('');
  }

  function toggle(id) {
    setTodos(todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  const left = todos.filter((t) => !t.done).length; // derived, never stale

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="New todo" />
      <button onClick={add}>Add</button>
      <ul>
        {todos.map((t) => (
          <li
            key={t.id}
            onClick={() => toggle(t.id)}
            style={{ textDecoration: t.done ? 'line-through' : 'none' }}
          >
            {t.text}
          </li>
        ))}
      </ul>
      <p>{left} left</p>
    </div>
  );
}

7 · Execution Flow

 VANILLA: click "Buy milk"
   listener -> t.done = true -> set li style
                               (count line never touched)  ==> "2 left"  STALE

 REACT: click "Buy milk"
   onClick -> toggle(id) -> setTodos(newArray)
        |
   React re-runs App()
        |
   left = todos.filter(!done).length  ==> 1
        |
   diff: li style changed, <p> text changed
        |
   DOM patched  ==> "1 left"  CORRECT

8 · Real-World Application

  • Shopping cart — badge, mini-cart, checkout total: classic drift bug when one is forgotten.
  • Chat — unread counts that stay "3" after you read the messages.
  • Movie filters — "Showing 12 results" not matching the visible grid.
  • Forms — innerHTML re-render erasing what the user was typing.

9 · Common Mistakes

Mistake 1: innerHTML with user text (XSS risk)

Wrong
// user types: <img src=x onerror=alert(1)>
list.innerHTML += '<li>' + input.value + '</li>';
// the browser runs the injected code
Fixed
// vanilla: use textContent
const li = document.createElement('li');
li.textContent = input.value;
list.appendChild(li);
// React: {text} in JSX is escaped automatically
<li>{text}</li>

Mistake 2: adding listeners again on every redraw

Wrong
function render() {
  list.innerHTML = todos.map(t => '<li>' + t + '</li>').join('');
  btn.addEventListener('click', () => add()); // new listener each time
}
// after 3 renders, one click runs add() 3 times
Fixed
btn.addEventListener('click', add); // once, outside render
function render() {
  list.innerHTML = '';
  todos.forEach(t => {
    const li = document.createElement('li');
    li.textContent = t;
    list.appendChild(li);
  });
}

Mistake 3: carrying vanilla habits into React

Wrong
function App() {
  function add() {
    document.getElementById('count').textContent = '5';
  }
  return <p id="count">0</p>;
}
// React doesn't know; its view and the DOM now disagree
// and the next update to that node can overwrite it
Fixed
function App() {
  const [count, setCount] = useState(0);
  return <p onClick={() => setCount(5)}>{count}</p>;
}

10 · Practice

Solution

Beginner 2

Why is innerHTML = userText dangerous?

Solution

The browser parses it as HTML, so attacker-written tags and event attributes can run code (XSS). Use textContent or JSX {text}.

Intermediate 1

Find the drift bug: a weather widget updates the temperature but not the "feels like" line.

Solution
function setTemp(t) {
  data.temp = t;
  tempEl.textContent = t + '°C';
  feelsEl.textContent = (t - 2) + '°C'; // the missing line
}

Intermediate 2

Rewrite it in React so the bug cannot happen.

Solution
function Weather() {
  const [temp, setTemp] = useState(30);
  return (
    <>
      <p>{temp}°C</p>
      <p>Feels like {temp - 2}°C</p>
      <button onClick={() => setTemp(temp + 1)}>Warmer</button>
    </>
  );
}

Challenge

Add a delete button to each todo in the React example; the "left" count must stay right.

Solution
function remove(id) {
  setTodos(todos.filter((t) => t.id !== id));
}

// inside map:
<li key={t.id}>
  <span onClick={() => toggle(t.id)}>{t.text}</span>
  <button onClick={() => remove(t.id)}>x</button>
</li>
// left is derived, so it is correct automatically

11 · Quick Revision

  • Manual DOM code = two copies of truth (data + DOM).
  • Every action must update every affected spot; easy to miss one.
  • innerHTML rebuilds lose input/focus and risk XSS.
  • Listeners added repeatedly fire multiple times.
  • React makes the DOM a result of state, so drift disappears.
  • In React, don't edit the DOM by hand for things React renders.

12 · Interview Corner

What is "imperative" UI code?

Code that lists the exact steps to change the screen (create, append, set text). Declarative code describes the final screen instead.

Why does manual DOM code get buggy as apps grow?

The number of update paths grows with actions x places. Each must be remembered, so some are missed and the UI shows stale data.

Does React escape text in JSX?

Yes. Values in {} are inserted as text, not HTML. Only dangerouslySetInnerHTML bypasses this.

Is direct DOM access ever okay in React?

Yes, through refs (useRef) for things React doesn't manage: focusing an input, measuring size, third-party widgets.

A · Concept in 30 Seconds

Manual DOM updates keep two copies of the truth: your data and the page. Every change must be copied by hand to every spot. Miss one and the UI drifts. React removes the second copy by computing the page from state.

B · Important Syntax

// vanilla
document.createElement('li'); el.appendChild(li);
el.textContent = 'safe text';
el.innerHTML = '<b>parsed as HTML</b>';   // risky with user input
el.addEventListener('click', fn);

// React
<li>{text}</li>               // auto-escaped
<button onClick={fn}>Go</button>

C · Must-Know Points

  • Imperative = steps; declarative = final result.
  • Stale UI happens when one update path is forgotten.
  • Derived values (counts, totals) should be computed, never stored twice.
  • innerHTML rebuilds destroy focus, typed text and old listeners.
  • innerHTML with user text is an XSS risk.
  • JSX escapes text by default.
  • In React, use state for display data and refs for rare direct DOM needs.

D · Interview Questions

Basic

What is DOM manipulation?

Using browser APIs (createElement, appendChild, textContent) to change the page from JavaScript.

Intermediate

Why not just re-set innerHTML of the whole app on every change?

It throws away and rebuilds every node: loses input values, focus, scroll, listeners, and is slow for big pages.

Advanced

How does React avoid the "rebuild everything" cost?

It re-runs components to get a new element tree, diffs it with the previous one, and patches only changed DOM nodes, keeping the rest (including input focus).

Tricky

Is the real DOM "slow"?

Not inherently. The costly part is unnecessary work and layout thrashing. React's benefit is mainly correctness and simpler code; efficiency is a bonus.

F · Debugging Questions

function render() {
  app.innerHTML = '<input id="q"><p>' + results.length + '</p>';
}
input.addEventListener('input', () => { search(); render(); });
// user loses focus after each key. Why?
Answer

innerHTML replaces the input with a brand-new element, so focus and the listener are lost. Update only the <p>, or use React, which keeps the same input node.

G · Scenario-Based Questions

A food app's cart badge shows 3 after checkout clears the cart. What's the root cause and fix?

The checkout code cleared the array but didn't update the badge DOM. Fix by making the badge read from one cart state (React {cart.length}).

H · Coding Challenges

Convert this vanilla code to React: a "Follow" button toggling text and a follower count.

let following = false, followers = 10;
btn.onclick = () => {
  following = !following;
  followers += following ? 1 : -1;
  btn.textContent = following ? 'Unfollow' : 'Follow';
  countEl.textContent = followers;
};
Solution
import { useState } from 'react';

export default function Follow() {
  const [following, setFollowing] = useState(false);
  const followers = 10 + (following ? 1 : 0); // derived
  return (
    <>
      <button onClick={() => setFollowing(!following)}>
        {following ? 'Unfollow' : 'Follow'}
      </button>
      <span> {followers} followers</span>
    </>
  );
}
