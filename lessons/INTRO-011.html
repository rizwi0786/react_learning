Client-side rendering

1. Visual Introduction

Client-side rendering is flat-pack furniture: the shop (server) sends you a box of parts (JavaScript), and you build the table (the page) at home (in the browser).

 time --->
 Server  | index.html (empty #root) | main.js bundle     | /api data (JSON)
         |            |             |        |           |       |
 Browser |  parse HTML  -> BLANK    | download, parse,   | fetch -> re-render
         |  screen (no content)     | run JS -> render   | with real data
         |                          | "Loading..."       |
         +--------------------------+--------------------+----------------
           user sees: nothing          user sees: spinner    user sees: page

2. Why Do We Need It?

  • Building HTML strings by hand for every data change is slow and error-prone.
  • CSR lets the browser own the UI: after the first load, every update is instant and local.
  • The server only serves static files and a JSON API, so hosting is cheap (any CDN).
Wrong
// server builds a full HTML page for every tiny change
app.get("/weather", async (req, res) => {
  const w = await getWeather();
  res.send("<h1>" + w.temp + " C</h1>"); // reload to refresh
});
Fixed
// server sends JSON; the browser renders
app.get("/api/weather", async (req, res) => {
  res.json(await getWeather());
});
// React: fetch -> setWeather -> UI updates, no reload

3. Core Concept

  • The server sends a nearly empty HTML shell: <div id="root"></div> plus a script tag.
  • The browser downloads and runs the JavaScript bundle; React builds all the DOM (client-side rendering, CSR).
  • Data is fetched after the first render, so you usually see a loading state first.
  • A plain Vite + React app is CSR by default.
  • Pros: cheap static hosting, rich interaction, fast navigation after load, low server work.
  • Cons: blank screen until JS runs (slow first paint on weak phones), weaker SEO and link previews, a "waterfall" of HTML → JS → data.
  • Measure with Core Web Vitals: Largest Contentful Paint (LCP) is often the CSR pain point.

4. Syntax

The HTML shell (index.html in a Vite app)

<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>SkyCast</title>
  </head>
  <body>
    <div id="root"></div>                       <!-- empty! -->
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>

The entry point that starts CSR

// src/main.jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App.jsx";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);

Fetch data after render

useEffect(() => {
  let ignore = false;
  fetch(url).then((r) => r.json()).then((d) => { if (!ignore) setData(d); });
  return () => { ignore = true; };
}, [url]);

5. Practical Example

A CSR weather card using the free Open-Meteo API (no key needed). Use with the main.jsx above.

// src/App.jsx
import { useEffect, useState } from "react";

const API =
  "https://api.open-meteo.com/v1/forecast" +
  "?latitude=28.61&longitude=77.21&current=temperature_2m,wind_speed_10m";

export default function App() {
  const [weather, setWeather] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignore = false;
    console.log("effect: fetching weather");

    fetch(API)
      .then((res) => {
        if (!res.ok) throw new Error("HTTP " + res.status);
        return res.json();
      })
      .then((data) => {
        if (ignore) return;            // stale request, skip
        console.log("data arrived");
        setWeather(data.current);      // { temperature_2m, wind_speed_10m, ... }
      })
      .catch((err) => {
        if (!ignore) setError(err.message);
      });

    return () => {
      ignore = true;
      console.log("cleanup");
    };
  }, []);

  if (error) return <p>Could not load weather: {error}</p>;
  if (!weather) return <p>Loading weather...</p>;

  return (
    <article>
      <h1>New Delhi</h1>
      <p>Temperature: {weather.temperature_2m} °C</p>
      <p>Wind: {weather.wind_speed_10m} km/h</p>
      <small>Rendered in your browser at {new Date().toLocaleTimeString()}</small>
    </article>
  );
}

Numbers are live, so yours will differ. Console in development with Strict Mode:

In a production build (npm run build + npm run preview), or without <StrictMode>:

data arrived
Strict Mode runs effects setup → cleanup → setup once more in development only, to catch missing cleanups. The ignore flag makes the first, cancelled request harmless.

Right-click → View Page Source: you will only see the empty <div id="root"></div>. The weather text exists only in the live DOM (Elements tab).

7. Execution Flow

 1. GET /                 -> index.html (~1 KB, empty #root)
 2. Browser parses HTML   -> sees <script type="module" src="...">
 3. GET /assets/index-*.js (bundle, often 100+ KB)
        |  screen is BLANK until this finishes
        v
 4. JS runs: createRoot(#root).render(<App />)
 5. First render: weather = null  -> DOM: "Loading weather..."
 6. Browser paints               (first content visible)
 7. useEffect runs (after paint) -> fetch(API)
        |  network round trip
        v
 8. JSON arrives -> setWeather(data.current)
 9. React re-renders -> diff -> updates DOM -> weather card visible (LCP)

 Waterfall: HTML --> JS --> data   (each step waits for the one before)

8. Real-World Application

  • Admin dashboards, internal tools: behind login, SEO is irrelevant; CSR is simplest.
  • Chat and email clients: long sessions; the first-load cost is paid once.
  • Online editors (docs, photo, design): heavy interaction lives in the browser.
  • Static hosting: a Vite build is just files in dist/, deployable to any CDN.
  • Public pages that must rank (shop product pages, movie pages) usually move to SSR or static generation (next lesson).

9. Common Mistakes

Mistake 1: No loading state (crash on first render)

Wrong
const [weather, setWeather] = useState(null);
// first render: weather is null
return <p>{weather.temperature_2m} °C</p>;
// TypeError: Cannot read properties of null
Fixed
if (!weather) return <p>Loading weather...</p>;
return <p>{weather.temperature_2m} °C</p>;

Mistake 2: Async function passed directly to useEffect

Wrong
useEffect(async () => {
  const res = await fetch(API);
  setWeather((await res.json()).current);
}, []);
// effect returns a Promise, not a cleanup function
Fixed
useEffect(() => {
  let ignore = false;
  async function load() {
    const res = await fetch(API);
    const data = await res.json();
    if (!ignore) setWeather(data.current);
  }
  load();
  return () => { ignore = true; };
}, []);

Mistake 3: Missing dependency array (infinite fetch loop)

Wrong
useEffect(() => {
  fetch(API).then((r) => r.json())
    .then((d) => setWeather(d.current));
}); // runs after EVERY render -> setState -> render -> ...
Fixed
useEffect(() => {
  fetch(API).then((r) => r.json())
    .then((d) => setWeather(d.current));
}, []); // run once after mount (twice in dev Strict Mode)

10. Practice

Beginner 1

Open View Page Source and the Elements tab on the weather app. What differs?

Solution

Source = the original HTML from the server (empty root). Elements = the live DOM after React rendered (full weather card). That gap is what "client-side rendering" means.

Beginner 2

Disable JavaScript in DevTools (Settings → Debugger → Disable JavaScript) and reload. What do you see and why?

Solution

A blank page. In CSR, all content is created by JavaScript, so no JS means no UI. Add a <noscript> message to the HTML shell.

Intermediate 1

Add a city picker (Delhi 28.61/77.21, Mumbai 19.08/72.88) that refetches when the city changes.

Solution 
const CITIES = {
  Delhi: [28.61, 77.21],
  Mumbai: [19.08, 72.88],
};
const [city, setCity] = useState("Delhi");

useEffect(() => {
  let ignore = false;
  const [lat, lon] = CITIES[city];
  setWeather(null); // show loading again
  fetch(`https://api.open-meteo.com/v1/forecast?latitude=${lat}&longitude=${lon}&current=temperature_2m,wind_speed_10m`)
    .then((r) => r.json())
    .then((d) => { if (!ignore) setWeather(d.current); });
  return () => { ignore = true; }; // drop slow, outdated responses
}, [city]);

<select value={city} onChange={(e) => setCity(e.target.value)}>
  {Object.keys(CITIES).map((c) => <option key={c}>{c}</option>)}
</select>

Intermediate 2

In DevTools → Network, throttle to "Slow 4G" and reload. List the request order and say which one delays the first content most.

Solution

Document → JS bundle (and CSS) → API call. The JS bundle usually delays the first content most, because nothing renders until it is downloaded and executed.

Challenge

Shrink the initial bundle: load a heavy ForecastChart component only when the user clicks "Show 7-day forecast".

Solution 
import { lazy, Suspense, useState } from "react";

const ForecastChart = lazy(() => import("./ForecastChart.jsx")); // separate chunk

export default function Forecast() {
  const [show, setShow] = useState(false);
  return (
    <>
      <button onClick={() => setShow(true)}>Show 7-day forecast</button>
      {show && (
        <Suspense fallback={<p>Loading chart...</p>}>
          <ForecastChart />
        </Suspense>
      )}
    </>
  );
}

Vite splits ForecastChart.jsx into its own file, downloaded on first click (code splitting).

11. Quick Revision

  • CSR = browser builds the page with JS; server sends an empty shell.
  • Entry: createRoot(el).render(<App />) from react-dom/client.
  • Load order: HTML → JS → render (loading) → fetch → re-render.
  • Pros: cheap hosting, rich UI, fast later updates.
  • Cons: blank first screen, weaker SEO, request waterfall.
  • Strict Mode double-runs effects in dev only; use cleanup.
  • Code splitting with lazy shrinks the first download.

12. Interview Corner

Q1. What is client-side rendering?

The server sends minimal HTML and a JS bundle; the browser runs the JS and React creates the DOM, then fetches data and re-renders.

Q2. Why can CSR hurt SEO?

The initial HTML has no content. Google can run JS but may index it later; many other crawlers and social link previews do not run JS at all.

Q3. Why does my fetch run twice in development?

React Strict Mode mounts, unmounts and remounts components in development to expose missing cleanup. Production runs it once.

Q4. How do you improve CSR first-load speed?

Code splitting (lazy + dynamic import()), smaller dependencies, caching, preloading critical data, and showing a meaningful skeleton early.

Q5. When is CSR the right choice?

Logged-in, highly interactive apps where SEO does not matter and users stay long: dashboards, chat, editors.

C. Must-Know Points

  • Initial HTML has no content; JS creates it.
  • Vite + React (no framework) = CSR by default.
  • First render happens before data; plan a loading state.
  • Effects run after the browser paints.
  • Strict Mode: effect setup → cleanup → setup in dev only.
  • Request waterfall: HTML → JS → data.
  • Output is static files; host on any CDN.
  • SEO and link previews are the main weakness.
  • Code splitting reduces time to first content.

D. Interview Questions

Basic

Where does rendering happen in CSR?

In the user's browser, by JavaScript.

Intermediate

What is a request waterfall in CSR?

Each request starts only after the previous finishes: HTML, then JS, then data (sometimes nested component data too), adding delays.

Advanced

How would you avoid the data waterfall in a CSR app?

Start the fetch earlier: in a router loader (React Router data mode), or kick it off at module/route level before render, and cache it with a data library.

Tricky

Does CSR mean the server does nothing?

No. It still serves files and APIs; it just does not build the HTML for each page.

  fetch("/api/movies").then((r) => r.json()).then(setMovies);
}, []);
return <ul>{movies.map((m) => <li key={m.id}>{m.title}</li>)}</ul>;
// TypeError on first load
Fix

G. Scenario-Based Questions

Marketing says shared links to your recipe pages show a blank preview in chat apps. Cause and fix?

Preview bots read raw HTML and do not run JS; the CSR shell has no title/description. Use SSR or prerender those pages.

Users on cheap phones see a white screen for 5 seconds.

The bundle is too large/slow to parse. Code-split routes, remove heavy libraries, and consider SSR for the first view.

H. Coding Challenges

Write a reusable useFetch(url) hook returning { data, error, loading } that ignores stale responses.

Solution 
import { useEffect, useState } from "react";

export function useFetch(url) {
  const [state, setState] = useState({ data: null, error: null, loading: true });
  useEffect(() => {
    let ignore = false;
    setState({ data: null, error: null, loading: true });
    fetch(url)
      .then((r) => { if (!r.ok) throw new Error("HTTP " + r.status); return r.json(); })
      .then((data) => !ignore && setState({ data, error: null, loading: false }))
      .catch((e) => !ignore && setState({ data: null, error: e.message, loading: false }));
    return () => { ignore = true; };
  }, [url]);
  return state;
}
