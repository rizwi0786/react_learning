Server-side rendering

1. Visual Introduction

SSR is a restaurant that brings your dish already cooked (HTML first). A moment later the waiter comes back with cutlery (JavaScript) so you can actually eat (click). Attaching the cutlery is called hydration.

 time --->
 Server   | runs <App /> -> HTML string |
          |          |                  |
 Browser  | paint FULL page (visible)   | download JS | hydrateRoot()
          | buttons look real but       |             | attaches click
          | do nothing yet              |             | handlers
          +-----------------------------+-------------+--------------
            user SEES content early        ...          user can USE it

 CSR:  blank ......... JS ......... content+interactive
 SSR:  content ....... JS ......... interactive  (hydration)

2. Why Do We Need It?

  • CSR shows a blank screen until JS runs, and crawlers may see nothing.
  • SSR runs the same React components on the server and sends finished HTML.
  • The browser shows content immediately; React then "hydrates" it to make it interactive.
Wrong
<!-- CSR response for /movies (View Source) -->
<body>
  <div id="root"></div>
  <script type="module" src="/assets/index.js"></script>
</body>
<!-- link preview: empty. slow phone: blank screen -->
Fixed
<!-- SSR response for /movies (View Source) -->
<body>
  <div id="root"><main><h1>Now Showing</h1>
    <ul><li>Space Pirates <button>Like (0)</button></li>
    ...</ul></main></div>
  <script type="module" src="/assets/client.js"></script>
</body>
<!-- content is in the HTML itself -->

3. Core Concept

  • On each request, the server renders components to an HTML string (server-side rendering, SSR).
  • Server APIs live in react-dom/server: renderToString, or streaming renderToPipeableStream (Node) / renderToReadableStream (Web Streams).
  • The browser paints that HTML at once: fast first content, good SEO and link previews.
  • Then the same JS bundle loads and calls hydrateRoot from react-dom/client.
  • Hydration = React walks the existing DOM, reuses it, and attaches event handlers. It does not rebuild it.
  • Server render and first client render must produce the same output, or you get a hydration mismatch.
  • On the server: no useEffect, no window, no clicks. Effects run only in the browser after hydration.
  • Most teams get SSR from a framework (React Router 7 framework mode, Next.js); these are framework features, not part of a plain Vite app.

4. Syntax

Server: render to HTML

import { renderToString } from "react-dom/server";

const html = renderToString(<App />);
// "<main><h1>Now Showing</h1>...</main>"

Client: hydrate, do not create

import { hydrateRoot } from "react-dom/client";

hydrateRoot(document.getElementById("root"), <App />);
// NOT createRoot(...).render(...) - that would rebuild the DOM

Streaming version (Node)

import { renderToPipeableStream } from "react-dom/server";

const { pipe } = renderToPipeableStream(<App />, {
  bootstrapScripts: ["/client.js"],
  onShellReady() {
    res.setHeader("Content-Type", "text/html");
    pipe(res); // send HTML in chunks as Suspense boundaries resolve
  },
  onShellError() {
    res.statusCode = 500;
    res.end("Something went wrong");
  },
});

5. Practical Example

A minimal SSR movie list using Vite in middleware mode with Express. Start from a Vite React app, then npm install express and add "type": "module" plus "dev": "node server.js" in package.json.

src/App.jsx (shared by server and client)

// src/App.jsx
import { useEffect, useState } from "react";

const MOVIES = [
  { id: 1, title: "Space Pirates" },
  { id: 2, title: "The Last Biryani" },
  { id: 3, title: "Monsoon Love" },
];

function MovieRow({ movie }) {
  const [likes, setLikes] = useState(0);
  return (
    <li>
      {movie.title}{" "}
      <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>
    </li>
  );
}

export default function App() {
  console.log("App render on", typeof window === "undefined" ? "server" : "client");

  useEffect(() => {
    // effects never run on the server
    console.log("hydrated - buttons now work");
  }, []);

  return (
    <main>
      <h1>Now Showing</h1>
      <ul>
        {MOVIES.map((m) => <MovieRow key={m.id} movie={m} />)}
      </ul>
    </main>
  );
}

src/entry-server.jsx

import { StrictMode } from "react";
import { renderToString } from "react-dom/server";
import App from "./App.jsx";

export function render() {
  return renderToString(
    <StrictMode>
      <App />
    </StrictMode>
  );
}

src/entry-client.jsx

import { StrictMode } from "react";
import { hydrateRoot } from "react-dom/client";
import App from "./App.jsx";

hydrateRoot(
  document.getElementById("root"),
  <StrictMode>
    <App />
  </StrictMode>
);

index.html (placeholder for server HTML)

<!doctype html>
<html lang="en">
  <head><meta charset="UTF-8" /><title>MovieTime</title></head>
  <body>
    <div id="root"><!--app-html--></div>
    <script type="module" src="/src/entry-client.jsx"></script>
  </body>
</html>

server.js (development server)

import fs from "node:fs/promises";
import express from "express";
import { createServer as createViteServer } from "vite";

const app = express();
const vite = await createViteServer({
  server: { middlewareMode: true },
  appType: "custom",
});
app.use(vite.middlewares);

app.use(async (req, res, next) => {
  try {
    let template = await fs.readFile("index.html", "utf-8");
    template = await vite.transformIndexHtml(req.originalUrl, template);
    const { render } = await vite.ssrLoadModule("/src/entry-server.jsx");
    const html = template.replace("<!--app-html-->", render());
    res.status(200).set({ "Content-Type": "text/html" }).end(html);
  } catch (e) {
    vite.ssrFixStacktrace(e);
    next(e);
  }
});

app.listen(5173, () => console.log("http://localhost:5173"));
This is the hand-made setup from the Vite SSR guide, good for learning. For real projects, a framework (React Router 7 framework mode, Next.js) handles routing, data loading, streaming and production builds for you.

7. Execution Flow

 1. Browser: GET /
 2. Express -> read index.html -> vite.transformIndexHtml
 3. ssrLoadModule("entry-server.jsx") -> render()
        |
        v
    renderToString(<App />)   (runs component bodies, NO effects)
    terminal: "App render on server"
        |
        v
 4. Replace <!--app-html--> with the HTML string -> send response
 5. Browser parses + PAINTS the movie list   (fast first content)
        |   buttons visible but not wired up yet
        v
 6. GET /src/entry-client.jsx (+ React)  -> JS runs
 7. hydrateRoot(#root, <App />)
        |   React renders in memory, compares with existing DOM
        |   match  -> reuse DOM nodes, attach onClick handlers
        |   mismatch -> error in console, React re-renders that part
        v
 8. useEffect runs -> "hydrated - buttons now work"
 9. Click Like -> setLikes -> normal client update from now on

8. Real-World Application

  • Online shops: product pages must rank in search and show price instantly.
  • News and recipe sites: articles readable before JS; rich link previews in chat apps.
  • Food delivery landing and restaurant pages: fast first view on slow mobile networks.
  • Personalised pages (logged-in home feed): server reads cookies and renders the user's data in the first HTML.
  • Not needed for: internal dashboards and tools behind login, where CSR is simpler and cheaper.

9. Common Mistakes

Mistake 1: Browser-only APIs during render

Wrong
function Theme() {
  const theme = localStorage.getItem("theme"); // runs on server too
  return <p>Theme: {theme}</p>;
}
// server: ReferenceError: localStorage is not defined
Fixed
function Theme() {
  const [theme, setTheme] = useState("light");
  useEffect(() => {
    // effects run only in the browser
    setTheme(localStorage.getItem("theme") ?? "light");
  }, []);
  return <p>Theme: {theme}</p>;
}

Mistake 2: Different output on server and client (hydration mismatch)

Wrong
function Clock() {
  return <p>Now: {new Date().toLocaleTimeString()}</p>;
}
// server says 10:00:01, client says 10:00:03
// -> hydration mismatch error in console
Fixed
function Clock() {
  const [time, setTime] = useState(null);
  useEffect(() => {
    setTime(new Date().toLocaleTimeString());
  }, []);
  return <p>Now: {time ?? "--:--"}</p>; // same on both at first
}

Mistake 3: createRoot instead of hydrateRoot on the client

Wrong
import { createRoot } from "react-dom/client";
createRoot(document.getElementById("root")).render(<App />);
// throws away the server HTML and builds it again
Fixed
import { hydrateRoot } from "react-dom/client";
hydrateRoot(document.getElementById("root"), <App />);
// reuses server HTML, only attaches handlers

Mistake 4: Random ids that differ per render

Wrong
const id = "email-" + Math.random();
<label htmlFor={id}>Email</label><input id={id} />
Fixed
import { useId } from "react";
const id = useId(); // same on server and client
<label htmlFor={id}>Email</label><input id={id} />

10. Practice

Beginner 1

Run the example, open View Page Source. Is "The Last Biryani" in the HTML? Would it be in the CSR app from INTRO-011?

Solution

Yes with SSR: it is inside #root in the raw HTML. In CSR, the source only had an empty <div id="root">.

Beginner 2

Throttle the network to "Slow 4G" and click Like the instant the page appears. What happens?

Solution

Nothing at first: the button is plain HTML until hydration attaches the handler. After the JS loads, clicks work. This gap is the "looks ready, is not ready" cost of SSR.

Intermediate 1

Add a "Welcome back, Asha" greeting that reads the name from localStorage without breaking SSR.

Solution 
function Greeting() {
  const [name, setName] = useState(null);
  useEffect(() => {
    setName(localStorage.getItem("name"));
  }, []);
  return <p>{name ? `Welcome back, ${name}` : "Welcome!"}</p>;
}

Server and first client render both show "Welcome!"; the name appears after hydration.

Intermediate 2

Pass the movie list from the server instead of hard-coding it, so both sides use identical data.

Solution 
// entry-server.jsx
export function render(movies) {
  return renderToString(<App movies={movies} />);
}
// server.js
const movies = await getMovies();
const html = template
  .replace("<!--app-html-->", render(movies))
  .replace("</body>",
    `<script>window.__MOVIES__ = ${JSON.stringify(movies).replace(/</g, "\\u003c")}</script></body>`);
// entry-client.jsx
hydrateRoot(document.getElementById("root"), <App movies={window.__MOVIES__} />);

Escaping < prevents a movie title from closing the script tag. Frameworks do this data hand-off for you.

Challenge

Switch entry-server.jsx to streaming with renderToPipeableStream so the shell is sent before slow parts finish.

Solution 
// entry-server.jsx
import { renderToPipeableStream } from "react-dom/server";
import App from "./App.jsx";

export function render(res, bootstrapModules) {
  const { pipe } = renderToPipeableStream(<App />, {
    bootstrapModules,                 // e.g. ["/src/entry-client.jsx"]
    onShellReady() {
      res.setHeader("Content-Type", "text/html");
      pipe(res);
    },
    onShellError() {
      res.statusCode = 500;
      res.end("Server error");
    },
    onError(err) {
      console.error(err);
    },
  });
}

Here React renders the whole document, so App must output <html>, <head> and <body>, and the client hydrates document instead of #root. Parts wrapped in <Suspense> stream in later.

11. Quick Revision

  • SSR = server runs components and sends ready HTML.
  • Client then calls hydrateRoot to attach handlers to that HTML.
  • Fast first content and strong SEO; interactivity waits for JS.
  • Server and first client render must match exactly.
  • No effects, window or localStorage on the server; use useEffect.
  • Streaming (renderToPipeableStream) sends HTML in chunks with Suspense.
  • Frameworks (React Router 7 framework mode, Next.js) provide SSR out of the box.

12. Interview Corner

Q1. What is server-side rendering?

Rendering React components to HTML on the server for each request, so the browser receives ready-to-display content.

Q2. What is hydration?

The client-side step where React, via hydrateRoot, attaches event handlers and state to server-rendered HTML instead of recreating the DOM.

Q3. What causes a hydration mismatch?

Different output between server and first client render: Date.now(), Math.random(), browser-only checks like typeof window in render output, locale differences, or invalid HTML nesting.

Q4. What are the costs of SSR?

Server compute per request, a running server instead of static files, more complex code (two environments), and a delay between seeing and using the page.

Q5. SSR vs static generation?

SSR renders on every request (fresh, personalised). Static generation renders once at build time (fastest, cacheable, but data is fixed until rebuild).

A. Concept in 30 Seconds

SSR: the server runs your React components and sends finished HTML, so users and crawlers see content right away. Then the JS loads and hydrateRoot wires up clicks on that same HTML. Server and client must render the same thing.

B. Important Syntax

// server
import { renderToString, renderToPipeableStream } from "react-dom/server";
const html = renderToString(<App />);

// client
import { hydrateRoot } from "react-dom/client";
hydrateRoot(document.getElementById("root"), <App />);

// stable ids across server and client
import { useId } from "react";
const id = useId();

C. Must-Know Points

  • HTML is generated per request on the server.
  • First content appears before JS runs.
  • hydrateRoot reuses DOM; createRoot would replace it.
  • Effects (useEffect, useLayoutEffect) do not run on the server.
  • Avoid window, document, localStorage during render.
  • Mismatch sources: time, random, browser checks, invalid nesting.
  • Use useId for ids that must match.
  • Streaming + Suspense sends the shell first, slow parts later.
  • Needs a server/edge runtime, not just a CDN.
  • Frameworks give SSR, routing and data loading together.

D. Interview Questions

Basic

Which package holds server rendering APIs?

react-dom/server (and react-dom/static for prerendering to static HTML).

Intermediate

Why does a button not respond right after an SSR page appears?

The HTML is visible but hydration has not attached the click handler yet; the JS is still loading.

Advanced

What does streaming SSR improve over renderToString?

renderToString waits for everything and cannot wait for data in Suspense (it sends the fallback). Streaming sends the shell immediately and streams each Suspense boundary's HTML as it resolves; parts can hydrate independently.

Tricky

Does SSR make the page interactive faster than CSR?

Not necessarily. It shows content faster; interactivity still waits for JS download and hydration, which can be similar to CSR.

E. Output-Based Questions

function App() {
  console.log("render");
  useEffect(() => console.log("effect"), []);
  return <p>Hi</p>;
}
// server: renderToString(<App />)   (production, no Strict Mode)
// client: hydrateRoot(root, <App />)
Logs?
Server terminal:  render
Browser console:  render
                  effect

The effect never runs on the server. With Strict Mode in development, the browser shows each line twice.

F. Debugging Questions

function Cart() {
  const isMobile = typeof window !== "undefined" && window.innerWidth < 600;
  return <p>{isMobile ? "Tap to order" : "Click to order"}</p>;
}
// Console: hydration error, text did not match
Fix

The server always renders "Click", a phone client renders "Tap". Render the same first, then switch in an effect:

const [isMobile, setIsMobile] = useState(false);
useEffect(() => setIsMobile(window.innerWidth < 600), []);

Or use a CSS media query for purely visual differences.

G. Scenario-Based Questions

Your shop's product pages rank poorly and show blank previews. The app is a Vite CSR app.

Move public pages to SSR or static prerendering, usually by adopting a framework (React Router 7 framework mode or Next.js) rather than hand-rolling SSR.

An SSR page shows a timestamp that "flickers" after load.

Server and client times differ, causing a mismatch and re-render. Render a placeholder and set the time in useEffect, or pass the server's timestamp as data.

H. Coding Challenges

Write a useIsClient() hook that returns false during SSR and the first client render, then true after hydration.

Solution 
import { useEffect, useState } from "react";

export function useIsClient() {
  const [isClient, setIsClient] = useState(false);
  useEffect(() => setIsClient(true), []);
  return isClient;
}

// usage
function MapWidget() {
  const isClient = useIsClient();
  return isClient ? <InteractiveMap /> : <p>Loading map...</p>;
}
