Static site generation

1. Visual Introduction

  • SSR (server-side rendering) = a restaurant that cooks each plate when you order it. Fresh, but every order costs kitchen time.
  • SSG (static site generation) = a bakery that bakes all the bread at 5 a.m. Customers just pick it up — instant, cheap, but it is “this morning’s” bread.
  • The “5 a.m. bake” is your build step (npm run build).
 SSR (every request)                 SSG (once, at build time)

 user ──► server                     npm run build
           │ fetch data                 │ fetch data
           │ render React → HTML        │ render React → HTML (every page)
           ▼                            ▼
 user ◄── fresh HTML                 dist/index.html, dist/movies/1.html ...
                                        │ upload to CDN
 cost: server work per visit            ▼
                                     user ──► CDN ──► ready-made HTML file
                                     cost: ~zero per visit
Key idea: SSG moves the rendering work from “every visit” to “once per build”.

2. Why Do We Need It?

  • A plain Vite React app (client-side rendering, CSR) ships an almost empty <div id="root">. The page is blank until JavaScript downloads and runs.
  • Search engines and link previews (WhatsApp, Slack) see less content.
  • SSR fixes that, but needs a running server for every visit.
  • For pages that rarely change (menus, blogs, docs, product catalogues), SSG gives full HTML with no server at all.
Wrong
<!-- CSR: what the browser first receives -->
<body>
  <div id="root"></div>
  <script type="module" src="/assets/index-a1b2.js"></script>
</body>
<!-- blank until JS runs; crawler sees nothing -->
Fixed
<!-- SSG: HTML already built at deploy time -->
<body>
  <div id="root">
    <h1>Now Showing</h1>
    <ul><li>Inception (2010)</li>...</ul>
  </div>
  <script type="module" src="/assets/index-a1b2.js"></script>
</body>
<!-- content visible at once; JS adds interactivity -->

3. Core Concept

  • Build-time rendering (static site generation, SSG): React runs on your machine or CI during the build, not in the browser and not per request.
  • Output: plain .html files + JS/CSS assets. Any static host or CDN (content delivery network) can serve them.
  • Hydration (hydration): the browser loads React, which attaches event handlers to the existing HTML using hydrateRoot.
  • Staleness: data is frozen at build time. New data → rebuild and redeploy.
  • Dynamic routes: you must list every path to pre-build (e.g. /movies/1, /movies/2).
  • React’s own API: prerender / prerenderToNodeStream from react-dom/static (React 19+) render a tree to HTML and wait for data.
  • Frameworks do the plumbing (framework-only): React Router 7 framework mode (prerender config), Next.js (generateStaticParams, output: 'export'), Astro.
StrategyHTML made when?Needs server?Freshness
CSR (client-side rendering)In the browserNoLive
SSR (server-side rendering)Every requestYesLive
SSG (static site generation)At buildNoAs of last build

4. Syntax

React’s low-level API (react-dom/static, Node)

import { prerenderToNodeStream } from 'react-dom/static';

const { prelude } = await prerenderToNodeStream(<App />);
// prelude = Node Readable stream of finished HTML
// waits for Suspense data before resolving

Hydrate the pre-built HTML (client)

import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

hydrateRoot(document.getElementById('root'), <App />);

React Router 7 framework mode (framework-only)

// react-router.config.ts
import type { Config } from '@react-router/dev/config';

export default {
  ssr: false,                 // no runtime server
  async prerender() {
    return ['/', '/menu', '/about'];   // paths built to HTML
  },
} satisfies Config;

Next.js App Router (framework-only)

// app/movies/[id]/page.jsx
export async function generateStaticParams() {
  return [{ id: '1' }, { id: '2' }];   // build /movies/1 and /movies/2
}

5. Practical Example

A movie listing page. We build the HTML ourselves with a tiny Node script, so you can see exactly what SSG does — no framework magic.

Setup

npm create vite@latest movie-ssg -- --template react
cd movie-ssg
npm install

src/movies.js — the “database” read at build time

export const movies = [
  { id: 1, title: 'Inception', year: 2010, rating: 8.8 },
  { id: 2, title: 'Spirited Away', year: 2001, rating: 8.6 },
  { id: 3, title: 'Dangal', year: 2016, rating: 8.3 },
];

src/App.jsx

import { useState } from 'react';

export default function App({ movies, builtAt }) {
  const [liked, setLiked] = useState([]);

  function toggle(id) {
    setLiked((prev) =>
      prev.includes(id) ? prev.filter((x) => x !== id) : [...prev, id]
    );
  }

  return (
    <main>
      <h1>Now Showing</h1>
      <p>Listing built at: {builtAt}</p>
      <ul>
        {movies.map((m) => (
          <li key={m.id}>
            {m.title} ({m.year}) – ⭐ {m.rating}{' '}
            <button onClick={() => toggle(m.id)}>
              {liked.includes(m.id) ? '♥ Liked' : '♡ Like'}
            </button>
          </li>
        ))}
      </ul>
      <p>You liked {liked.length} movie(s).</p>
    </main>
  );
}

src/main.jsx — hydrate instead of createRoot

import { StrictMode } from 'react';
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';
import { movies } from './movies.js';

// Must pass the SAME props used at build time
const builtAt = document.getElementById('root').dataset.builtAt;

hydrateRoot(
  document.getElementById('root'),
  <StrictMode>
    <App movies={movies} builtAt={builtAt} />
  </StrictMode>
);

prerender.mjs — runs once after vite build

// Run with Vite's SSR loader so JSX works in Node
import fs from 'node:fs/promises';
import { createServer } from 'vite';

const vite = await createServer({ server: { middlewareMode: true }, appType: 'custom' });
const { prerenderToNodeStream } = await import('react-dom/static');
const { createElement } = await import('react');
const { default: App } = await vite.ssrLoadModule('/src/App.jsx');
const { movies } = await vite.ssrLoadModule('/src/movies.js');

const builtAt = new Date().toISOString().slice(0, 16).replace('T', ' ');
const { prelude } = await prerenderToNodeStream(
  createElement(App, { movies, builtAt })
);

let html = '';
for await (const chunk of prelude) html += chunk;

const template = await fs.readFile('dist/index.html', 'utf8');
const page = template.replace(
  '<div id="root"></div>',
  `<div id="root" data-built-at="${builtAt}">${html}</div>`
);
await fs.writeFile('dist/index.html', page);
await vite.close();
console.log('Pre-rendered dist/index.html at', builtAt);

package.json scripts

"scripts": {
  "dev": "vite",
  "build": "vite build && node prerender.mjs",
  "preview": "vite preview"
}
Note: the script is plain JavaScript (.mjs) with no JSX — it uses createElement. The JSX inside App.jsx is compiled by vite.ssrLoadModule. In real projects a framework does all of this for you.

8. Real-World Application

  • Restaurant menu site: menu changes weekly → rebuild weekly. Pages load instantly from a CDN.
  • Recipe or food blog: thousands of posts, each pre-built; great for search ranking.
  • Product docs / help centre: content in Markdown, rebuilt on every edit.
  • Shop marketing pages: home, “About”, category landing pages as SSG; the cart and checkout stay client-side or SSR.
  • When SSR wins instead: per-user pages (order history), live data (stock prices, delivery tracking), or millions of pages that are too slow to pre-build.
  • Hybrid (framework-only): Next.js incremental static regeneration (ISR) rebuilds a single page in the background after a timeout — a middle ground.
QuestionIf yes →
Same HTML for every visitor?SSG candidate
Data changes less often than you can rebuild?SSG
Depends on cookies / logged-in user?SSR or CSR
Must be up-to-the-second?SSR or CSR fetch

9. Common Mistakes

Mistake 1: Using browser-only values during build-time render

Wrong
export default function App() {
  // Crashes at build: window is not defined in Node
  const width = window.innerWidth;
  return <p>Screen: {width}px</p>;
}
Fixed
import { useEffect, useState } from 'react';

export default function App() {
  const [width, setWidth] = useState(null);
  useEffect(() => {
    // runs only in the browser, after hydration
    setWidth(window.innerWidth);
  }, []);
  return <p>Screen: {width ?? '…'}px</p>;
}

Mistake 2: Hydration mismatch (different output on build vs browser)

Wrong
export default function App() {
  // build-time time ≠ browser time → mismatch error
  return <p>Now: {new Date().toLocaleTimeString()}</p>;
}
Fixed
export default function App({ builtAt }) {
  // same value passed on build AND hydrate
  return <p>Built: {builtAt}</p>;
}

Mistake 3: Calling createRoot on pre-rendered HTML

Wrong
import { createRoot } from 'react-dom/client';
// throws away the static HTML and re-creates it
createRoot(root).render(<App />);
Fixed
import { hydrateRoot } from 'react-dom/client';
// reuses the existing HTML, attaches events
hydrateRoot(root, <App />);

Mistake 4: Expecting new data without a rebuild

  • Adding a movie to the database does nothing for an SSG page until you run the build again (or use a framework feature like ISR, or fetch fresh data on the client).

10. Practice

Beginner 1

For each page, pick CSR, SSR or SSG: (a) a pizza shop “Our Story” page, (b) a user’s order history, (c) a weather page updated every minute.

Solution
  • (a) SSG — same for everyone, rarely changes.
  • (b) SSR or CSR — per-user, needs login.
  • (c) SSR or CSR with client fetching — changes too often to rebuild.

Beginner 2

Which function should main.jsx call when the HTML was pre-built: createRoot or hydrateRoot? Why?

Solution

hydrateRoot from react-dom/client. It keeps the existing HTML and attaches event handlers. createRoot(...).render() would replace the static markup.

Intermediate 1

Extend prerender.mjs to write one file per movie: dist/movies/1.html, 2.html… using a MovieDetail component.

Solution 
// after loading movies and the template:
const { default: MovieDetail } = await vite.ssrLoadModule('/src/MovieDetail.jsx');
await fs.mkdir('dist/movies', { recursive: true });

for (const movie of movies) {
  const { prelude } = await prerenderToNodeStream(
    createElement(MovieDetail, { movie })
  );
  let html = '';
  for await (const chunk of prelude) html += chunk;
  const page = template.replace('<div id="root"></div>', `<div id="root">${html}</div>`);
  await fs.writeFile(`dist/movies/${movie.id}.html`, page);
}

(For hydration on these pages you would also need main.jsx to pick the right component per URL — that is what a router/framework handles.)

Intermediate 2

Write a React Router 7 framework-mode config that pre-renders / plus one path per recipe from getRecipes(), with no runtime server.

Solution 
// react-router.config.ts
import type { Config } from '@react-router/dev/config';
import { getRecipes } from './app/data';

export default {
  ssr: false,
  async prerender() {
    const recipes = await getRecipes();
    return ['/', ...recipes.map((r) => `/recipes/${r.slug}`)];
  },
} satisfies Config;

Challenge

A food-delivery site has 50,000 restaurant pages. Menus change a few times a day; ratings change every minute. Design a rendering plan.

Solution
  • Pre-build only the top ~1,000 popular restaurants at build; render the rest on demand (framework features such as Next.js ISR or on-demand SSR + CDN caching).
  • Menu: static/cached, revalidated a few times a day.
  • Ratings: fetch on the client after hydration (small widget), so the static HTML never needs rebuilding for them.
  • Cart/checkout: client-side, per-user.

11. Quick Revision

  • SSG = render React to HTML once at build time.
  • Output is static files → host on any CDN, no server.
  • Browser uses hydrateRoot to make the HTML interactive.
  • Data is as old as the last build.
  • Avoid window, dates and random values in render output — move them into useEffect.
  • React API: prerender / prerenderToNodeStream in react-dom/static.
  • Frameworks (React Router 7, Next.js, Astro) automate routes, data and file writing.

12. Interview Corner

Q1. What is static site generation?

Rendering pages to HTML during the build, so each request just serves a pre-made file from a CDN. React hydrates it in the browser for interactivity.

Q2. When does SSG beat SSR?

When content is the same for all users and changes less often than you can rebuild: lower cost, faster time-to-first-byte (TTFB), no server to scale or secure.

Q3. What is a hydration mismatch?

The HTML React renders in the browser differs from the pre-built HTML (e.g. dates, Math.random(), window checks). React reports an error and re-renders that part on the client.

Q4. Does a Vite React app do SSG by default?

No. vite build outputs a CSR app with an empty root. You need your own prerender script or a framework (e.g. React Router 7 framework mode with prerender).

Q5. How do you show fresh data on an SSG page?

Rebuild and redeploy, use a framework’s incremental regeneration (framework-only), or fetch the changing part on the client after hydration.

A. Concept in 30 Seconds

SSG (static site generation) runs React at build time to produce finished HTML files. A CDN serves them instantly; React then hydrates them for clicks. Perfect for content that is the same for everyone and changes slowly. Trade-off: data is only as fresh as the last build.

B. Important Syntax

// Build-time render (Node)
import { prerenderToNodeStream } from 'react-dom/static';
const { prelude } = await prerenderToNodeStream(<App />);

// Web-streams version (Node 18+, edge, Deno)
import { prerender } from 'react-dom/static';
const { prelude } = await prerender(<App />);
const html = await new Response(prelude).text();

// Browser
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />);

// React Router 7 framework mode
export default { ssr: false, prerender: ['/', '/menu'] };

C. Must-Know Points

  1. HTML is generated once per build, not per request.
  2. Output = static files; no Node server needed in production.
  3. hydrateRoot, not createRoot, on pre-rendered HTML.
  4. Build render and first browser render must produce identical output.
  5. prerender APIs wait for Suspense data; renderToString does not.
  6. Dynamic routes must be listed in advance.
  7. Build time grows with page count.
  8. Per-user or live data → SSR/CSR, or client-side fetch after hydration.
  9. ISR and generateStaticParams are Next.js (framework-only) features.
  10. Create React App is deprecated — start with Vite or a framework.

D. Interview Questions

Basic

What does SSG output?

Static .html files plus JS/CSS bundles, ready for any static host.

Name one benefit over CSR.

Content is visible before JS loads — better first paint and SEO (search engine optimisation).

Intermediate

Why can’t you read localStorage while pre-rendering?

The render runs in Node at build time; browser APIs don’t exist there. Read it in useEffect, which runs only in the browser.

Difference between renderToString and prerender?

renderToString is synchronous and emits Suspense fallbacks; prerender (react-dom/static) is async and waits for all data so the HTML is complete.

Advanced

How would you pre-build 1 million product pages?

You usually don’t. Pre-build the popular subset; generate the rest on demand and cache at the CDN (framework features like ISR or SSR + cache headers).

What is partial pre-rendering in React 19.2?

React 19.2 added APIs to pre-render a static shell and later resume rendering the dynamic parts (e.g. resume in react-dom/server, resumeAndPrerender in react-dom/static). Mainly used by frameworks.

Tricky

An SSG page shows yesterday’s price even after a DB update. Bug?

Not a React bug — it is by design. The page needs a rebuild, a revalidation strategy, or a client-side fetch for the price.

Is SSG the same as “no JavaScript”?

No. The HTML is static, but React’s JS still loads to hydrate unless the page has no interactivity (e.g. Astro islands ship JS only where needed).

F. Debugging Questions

Build fails with ReferenceError: document is not defined.

const theme = document.body.dataset.theme;
export default function App() { return <p>{theme}</p>; }
Fix

Top-level code runs in Node during the prerender. Move DOM access into useEffect and keep a safe default for the first render.

Console: “Hydration failed because the server rendered HTML didn’t match the client.”

<p>Lucky number: {Math.floor(Math.random() * 10)}</p>
Fix

Random values differ between build and browser. Generate the number in useEffect, or pass a fixed value from the build.

G. Scenario-Based Questions

A café wants a 5-page site, menu updated monthly, cheapest hosting.

SSG on a free static host/CDN. Rebuild when the menu changes.

A movie site: film pages static, but “seats left” must be live.

SSG the film pages; fetch seat counts on the client after hydration (or with TanStack Query).

An admin dashboard behind login.

Not an SSG fit — CSR (Vite SPA) or SSR. Content is per-user and private.

Make this component safe for SSG (it shows the visitor’s local time).

export default function Clock() {

}
Solution 
import { useEffect, useState } from 'react';

  const [time, setTime] = useState(null);

    setTime(new Date().toLocaleTimeString());
  }, []);
