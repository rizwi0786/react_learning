JSX transformation

1. Visual Introduction

  • Think of a restaurant order slip. The waiter hears "two dosas, no onion" (JSX) and writes a standard slip the kitchen understands (a jsx() call).
  • The compiler is the waiter: it rewrites every tag into a function call before the browser sees your code.
  • Since React 17 the compiler also adds the import for you — this is the automatic runtime (automatic JSX runtime).
 YOUR FILE (App.jsx)                     COMPILED FILE (what the browser gets)
┌──────────────────────────────┐        ┌───────────────────────────────────────────────┐
│ function Dish({ name }) {    │        │ import { jsx as _jsx } from                   │
│   return (                   │        │        "react/jsx-runtime";   ← auto-added    │
│     <li className="dish">    │ ─────► │ function Dish({ name }) {                     │
│       {name}                 │compile │   return _jsx("li", {                         │
│     </li>                    │        │     className: "dish",                        │
│   );                         │        │     children: name     ← children INSIDE props│
│ }                            │        │   });                                         │
└──────────────────────────────┘        │ }                                             │
                                        └───────────────────────────────────────────────┘
Key idea: in the automatic runtime, children go inside props, and key is a separate argument.

2. Why Do We Need It?

  • Old (classic) runtime compiled to React.createElement, so every JSX file needed import React from 'react'.
  • Forgetting it → ReferenceError: React is not defined.
  • Automatic runtime: no manual import, slightly smaller bundles, and a faster element-creation path.
Classic runtime (old)
import React from 'react'; // required!

function Hello() {
  return <h1>Hi</h1>;
}

// compiles to:
// React.createElement("h1", null, "Hi");
Automatic runtime (now)
// no React import needed

function Hello() {
  return <h1>Hi</h1>;
}

// compiles to:
// import { jsx as _jsx } from "react/jsx-runtime";
// _jsx("h1", { children: "Hi" });

3. Core Concept

  • Entry point: react/jsx-runtime (production) and react/jsx-dev-runtime (development).
  • Functions emitted:
    • jsx(type, props, key) — zero or one child.
    • jsxs(type, props, key) — several static children (written side by side in the source).
    • jsxDEV(...) — dev builds; adds debug info (file name, line) for better warnings.
    • Fragment — imported when you write <>…</>.
  • type: lowercase tag → string ("li"); Capitalised → the variable (Dish); dotted → member (Menu.Item).
  • props: all attributes + children. key is pulled out into the 3rd argument.
  • ref: in React 19, ref is a normal prop for function components (no forwardRef needed).
  • Result: a React element object, e.g. { $$typeof, type, key, props }. Rendering happens later.
  • The calls are marked /*#__PURE__*/ so minifiers can drop unused elements (tree-shaking).

4. Syntax

// 1. One child → jsx
<p>Hello</p>
_jsx("p", { children: "Hello" })

// 2. Multiple static children → jsxs (children is an array)
<p>Hi {user}!</p>
_jsxs("p", { children: ["Hi ", user, "!"] })

// 3. Component with props
<MovieCard title="Dune" rating={8.5} />
_jsx(MovieCard, { title: "Dune", rating: 8.5 })

// 4. key is the 3rd argument, NOT a prop
<li key={todo.id}>{todo.text}</li>
_jsx("li", { children: todo.text }, todo.id)

// 5. Fragment
<><h2>A</h2><p>B</p></>
_jsxs(_Fragment, { children: [_jsx("h2", { children: "A" }), _jsx("p", { children: "B" })] })

// 6. Spread props
<button {...btnProps} disabled>Pay</button>
_jsx("button", { ...btnProps, disabled: true, children: "Pay" })

// 7. A list from map is ONE dynamic child → jsx (keys are checked)
<ul>{items.map((i) => <li key={i}>{i}</li>)}</ul>
_jsx("ul", { children: items.map((i) => _jsx("li", { children: i }, i)) })
Exact output differs slightly between compilers (Babel writes _jsx, esbuild/Oxc may write jsx or jsx2). The shape — type, props with children, key — is the same.

5. Practical Example

Peek inside the elements JSX creates, and build one by hand. Vite React app, replace src/App.jsx.

// src/App.jsx
import { jsx } from 'react/jsx-runtime'; // learning only — normally the compiler adds this

const todos = [
  { id: 't1', text: 'Buy milk' },
  { id: 't2', text: 'Call mom' },
];

// Element written in JSX
const fromJsx = <li key="t1" className="todo">Buy milk</li>;

// The same element built by hand
const byHand = jsx('li', { className: 'todo', children: 'Buy milk' }, 't1');

// Logged once at module load (outside a component, so Strict Mode
// double-rendering does not repeat it)
console.log('type:', fromJsx.type);
console.log('key:', fromJsx.key);
console.log('props:', fromJsx.props);
console.log('same shape?', fromJsx.type === byHand.type &&
  fromJsx.key === byHand.key &&
  JSON.stringify(fromJsx.props) === JSON.stringify(byHand.props));

function TodoItem({ text }) {
  return <li className="todo">{text}</li>;
}

export default function App() {
  return (
    <>
      <h1>My Todos</h1>
      <ul>
        {todos.map((t) => (
          <TodoItem key={t.id} text={t.text} />
        ))}
        {byHand /* a hand-built element renders like any other */}
      </ul>
    </>
  );
}

Now see the real compiled code: run npm run dev, open DevTools > Sources (or Network), and open src/App.jsx — Vite serves the transformed file. Its dev output uses jsxDEV from react/jsx-dev-runtime.

Console (development build):

  • key is not inside props.

  • The hand-built element renders exactly like JSX ones. Its key t1 does not clash with the mapped t1, because keys only need to be unique within the same array.

7. Execution Flow

 ① Write          <TodoItem key={t.id} text={t.text} />
                        │
 ② Compile (Vite)       ▼   at build / dev-serve time, NOT in the browser
                  import { jsxDEV } from "react/jsx-dev-runtime"   (dev)
                  import { jsx }    from "react/jsx-runtime"       (prod)
                  jsx(TodoItem, { text: t.text }, t.id)
                        │
 ③ Run (browser)        ▼   when App() renders
                  { $$typeof: Symbol(react.transitional.element),
                    type: TodoItem, key: "t1", props: { text: "Buy milk" } }
                        │
 ④ Render               ▼   React calls TodoItem({ text: "Buy milk" })
                  → returns another element: { type: "li", ... }
                        │
 ⑤ Commit               ▼   react-dom creates / updates <li class="todo">

8. Real-World Application

  • Reading errors: stack traces and bundle code show jsx(...) / jsxDEV(...) calls — you now know they are your JSX tags.
  • Using other libraries: Preact or Emotion change the source with jsxImportSource, so JSX calls their runtime instead of React's.
  • TypeScript projects: "jsx": "react-jsx" in tsconfig.json means "automatic runtime".
  • Lists in a chat app: knowing key is separate from props explains why props.key is undefined inside a message component.

9. Common Mistakes

Mistake 1: Reading key from props

Wrong
function Message({ key, text }) {
  return <p>#{key}: {text}</p>; // key is undefined
}
<Message key={m.id} text={m.text} />
// Dev warning: `key` is not a prop.
Fixed
function Message({ id, text }) {
  return <p>#{id}: {text}</p>;
}
<Message key={m.id} id={m.id} text={m.text} />

Mistake 2: Lowercase component name

Wrong
function cartBadge() { return <span>3</span>; }

<cartBadge />
// compiles to jsx("cartBadge", {}) → a string!
// Renders an unknown <cartbadge> tag + warning
Fixed
function CartBadge() { return <span>3</span>; }

<CartBadge />
// compiles to jsx(CartBadge, {}) → your function

Mistake 3: Mixing runtimes in an old project

Wrong
/** @jsxRuntime classic */
// file forced to classic runtime, but no React import
export const Tag = () => <b>New</b>;
// ReferenceError: React is not defined
Fixed
// Remove the pragma and use the automatic runtime
// (Vite's React plugin default)
export const Tag = () => <b>New</b>;

Challenge

Compile the whole component by hand, including the import line:

function Weather({ days }) {
  return (
    <>
      <h2>Forecast</h2>
      <ul>
        {days.map((d) => <li key={d.day}>{d.day}: {d.temp}°</li>)}
      </ul>
    </>
  );
}
Show solution
import { jsx as _jsx, jsxs as _jsxs, Fragment as _Fragment } from "react/jsx-runtime";

function Weather({ days }) {
  return _jsxs(_Fragment, {
    children: [
      _jsx("h2", { children: "Forecast" }),
      _jsx("ul", {
        children: days.map((d) =>
          _jsxs("li", { children: [d.day, ": ", d.temp, "°"] }, d.day)
        ),
      }),
    ],
  });
}

ul uses jsx (one dynamic child: the array). Each li uses jsxs (four static children).

11. Quick Revision

  • Automatic runtime = compiler imports jsx/jsxs from react/jsx-runtime for you.
  • No more import React just for JSX.
  • Signature: jsx(type, props, key); children live in props.children.
  • jsxs = multiple static children; jsx = zero/one child.
  • Dev builds use jsxDEV from react/jsx-dev-runtime.
  • key is never in props; React 19 treats ref as a regular prop.
  • Lowercase tag → string; Capitalised → component variable.

12. Interview Corner

What changed with the new JSX transform (React 17)?

Compilers stopped emitting React.createElement and instead auto-import jsx/jsxs from react/jsx-runtime. No React import is needed in JSX files, and the element-creation path is simpler.

Difference between jsx and jsxs?

Both create elements. jsxs is used when children is a static array written in the source, so React knows those children don't need keys. jsx handles zero/one child (including a dynamic array, which is key-checked).

Why isn't key available as a prop?

The compiler passes it as a separate argument. React uses it internally for reconciliation; pass the value again under another prop name if the child needs it.

Should you call jsx() directly in app code?

No. It's an entry point for compilers. In hand-written non-JSX code use createElement, which is the public API for that.

A. Concept in 30 Seconds

Your JSX becomes jsx(type, props, key) calls. The compiler auto-imports them from react/jsx-runtime. Children go in props.children; key is separate. Each call returns an element object.

B. Important Syntax

import { jsx, jsxs, Fragment } from "react/jsx-runtime";      // prod
import { jsxDEV } from "react/jsx-dev-runtime";              // dev

jsx("img", { src: "/tea.png", alt: "Tea" })                  // <img src="/tea.png" alt="Tea" />
jsxs("p", { children: ["Qty: ", qty] })                       // <p>Qty: {qty}</p>
jsx(Row, { name }, id)                                        // <Row key={id} name={name} />

// tsconfig.json → "jsx": "react-jsx"   (automatic runtime)
// file pragma   → /** @jsxImportSource preact */

C. Must-Know Points

  1. Automatic runtime is the default in Vite's React plugin and modern tools.
  2. Classic runtime = React.createElement; needs React in scope.
  3. Children are part of props in the automatic runtime.
  4. key → 3rd argument; never readable as a prop.
  5. jsxs for static multiple children; jsx otherwise.
  6. Dev uses jsxDEV for richer warnings.
  7. Fragment shorthand imports Fragment from the runtime.
  8. jsxImportSource swaps the runtime package (e.g. Preact).
  9. Elements are objects; React 19 marks them with Symbol(react.transitional.element).
  10. In React 19, ref is a normal prop on function components.

D. Interview Questions

Basic

Do you still need import React from 'react' in every component?

No, not with the automatic runtime. Import only what you use, e.g. import { useState } from 'react'.

Which package path does the compiler import from?

react/jsx-runtime (and react/jsx-dev-runtime in development).

Intermediate

Where does children go in a jsx() call?

Inside the props object as props.children — not as extra arguments like createElement.

What is /*#__PURE__*/ in compiled output?

An annotation telling minifiers the call has no side effects, so it can be removed if the result is unused.

Advanced

How would you make JSX compile to Preact?

Set the JSX import source to preact (compiler option or /** @jsxImportSource preact */). JSX then calls preact/jsx-runtime.

Tricky

What does <div {...props} key="a" /> compile to in Babel?

Babel falls back to createElement (imported from react) when key comes after a spread, to keep old semantics. Put key before the spread to keep the fast jsx() path.

Is a component function called when JSX is evaluated?

No. jsx(TodoItem, props) only creates an object. React calls TodoItem later, during rendering.

F. Debugging Questions

An old file throws React is not defined. Why?

/** @jsx React.createElement */
export const Chip = () => <span>Veg</span>;
Answer

The pragma forces the classic transform, which emits React.createElement, but React isn't imported. Remove the pragma (automatic runtime) or add import React from 'react'.

A component renders as <orderrow> in the DOM. Why?

const orderRow = ({ id }) => <tr><td>{id}</td></tr>;
<orderRow id={7} />
Answer

Lowercase → compiled as the string "orderRow". Rename to OrderRow.

G. Scenario-Based Questions

Your bundle analyser shows thousands of jsx( calls. Is that a problem?

No — that's your JSX. Each call is cheap object creation. Performance work belongs in rendering (fewer re-renders), not in the transform.

Migrating a 2019 project: lots of import React from 'react' lines that are only for JSX. Remove them?

Yes, once the compiler uses the automatic runtime. Keep imports that use React.something or switch to named imports (useState, etc.).

H. Coding Challenges

Write the compiled output for:

<button type="button" onClick={add} disabled={!stock}>
  Add {qty}
</button>
Solution
_jsxs("button", {
  type: "button",
  onClick: add,
  disabled: !stock,
  children: ["Add ", qty],
})

Leading/trailing line-break whitespace is trimmed by the JSX rules, so the first child is "Add ".
